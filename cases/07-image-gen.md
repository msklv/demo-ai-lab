# Кейс 07 — картинка на своей карте: Z-Image-Turbo (vLLM-Omni, fp8)

## Требования: модели на GPU

| Деплой в GPUStack | VRAM | Действие человека в UI |
|---|---|---|
| `Z-Image-Turbo` (категория `image`, `vLLM 0.22.1 --omni --quantization fp8`; id 15, маршрут 12) | **12.4 GiB** простой, **15.3 GiB** пик на 1024² | `Start` |

- Набор **несовместим со стражем** (`util 0.80`, ≈12.7 GiB), как и 27B: `llm.`/`llm-svc.` в кейсе отдают
  `503`, внешних вызовов нет. `POST /v1/images/generations` идёт мимо `ai-qwen-guard` (плагин текстовый, на
  чат-маршруте) — контент периметр не пересекает, модерировать нечего; на сцене это проговаривается вслух.
- 780M для генерации не годится (минуты на кадр); `bge` на iGPU трогать не нужно.

## Сценарий показа

1. **Тезис:** картинка — самый очевидный кандидат «отдать в облако», и всё равно не отдаём: промпт и
   результат не покидают стенд, платить за изображение некому.
2. `Model Service → Deployments`: карточка `Z-Image-Turbo`, бэкенд vLLM-Omni, 8 шагов инференса (NFE), квант
   `fp8` — всё видно в параметрах.
3. **Playground картинок:** `Size` **512×512**, готовый английский промпт, `Submit` → картинка за **3–4 с**.
   Промпт на экране целиком: уходит только текст в локальную модель.
4. Второй и третий промпт — фотореализм и **рендер текста внутри картинки** (EN/ZH — сильная сторона);
   русский — третьим, с честным комментарием «где тонко».
5. **Цифры:** 3–3,6 с на кадр 512², 15.3 GiB VRAM, 8 шагов против 20–50 у неразогнанных диффузий, fp8 (6B DiT
   в ≈6 GiB); сравнение с ценой облака за то же число картинок и отправленных промптов.
6. Ограничения вслух: разрешение и качество кириллицы в кадре, рукописный/смешанный текст, модель не
   «понимает» смысл картинки как VLM.
7. (опция) тот же эндпоинт в чате: OWU → `Admin → Settings → Images → OpenAI API` на `api.` — картинка
   рождается прямо в переписке.

## Критерий успеха

`POST /v1/images/generations` через `api.` → `200`, непустой PNG **512×512 при 8 шагах**, время **≤4 с**
(замер 3.0–3.6), пик VRAM **≤15.5 GiB** (замер 15.3), 0 `CUDA out of memory` и 0 рестартов пода за прогон.

## Скорость (замер 04.11 через `api.`)

| Режим | Время | Замечание |
|---|---|---|
| **512×512, 8 шагов** | **3.0–3.6 с** | **сценический режим** (решение владельца): композиция, свет и **текст в кадре** держатся — на промпте с вывеской `MORNING BREW` без единой опечатки |
| 1024×1024, 8 шагов (штатные NFE) | 12.8–13.4 с | опция для скриншотов и слайдов |
| 1024×1024, 6 / 4 шага | 10.4 / 7.7 с | заметная потеря детализации — не берём |

Плата за 512² — микродетали (0.26 Мп): на сцене кадр идёт **в окне/на слайде в натуральную величину**, а не
растянутым на весь экран. `--cache-backend tea_cache` на 8 шагах не помогает (12.9–13.2 с), конфигурация
откачена на чистый fp8. Уникальность кадров проверена по `md5` (разные `seed` → разные файлы; одинаковый
размер PNG при этом нормален — фиксированная компрессия).

## Как развёрнуто (рецепт, проверенный 04.11)

| Шаг | Значение |
|---|---|
| Веса | HF `Tongyi-MAI/Z-Image-Turbo` целиком, **32.9 GB** на диске: DiT FP32 24.6 GB (3 шарда) + энкодер `Qwen3-4B` BF16 7.95 GB + VAE 0.17 GB |
| Бэкенд | `vLLM` **0.22.1**, раннер `gpustack/runner:cuda13.0-vllm0.22.1` (host driver 595.99.02 / CUDA 13.2) |
| Параметры | `--omni --quantization fp8` — онлайн-квантование DiT; энкодер и VAE остаются BF16 |
| Заявка VRAM | `GPUSTACK_MODEL_VRAM_CLAIM=16106127360` (15 GiB): карточка каталога просит **23 GiB** (bf16-путь), с ней инстанс не сел бы |
| Размещение | `worker_selector: k8s-04`, категория `image` |
| Публикация в `/v1` | `ModelRoute` id 12 → `model_id 15`: без маршрута `/v1/*` отдаёт `404 Model not found` |
| Старт → `running` | ≈60–70 с при прогретых весах и образе — укладывается в переход 06 → 07 |

Квант — **fp8, не int8**: на `sm_120` (5070 Ti) int8-ядра cutlass не собраны. Выигрыш тот же: DiT из 12 GiB
становится ≈6 GiB.

## Бюджет VRAM на 5070 Ti (15.93 GiB)

| Чекпойнт | DiT + энкодер + VAE | Итог |
|---|---|---|
| bf16 как есть | 11.5 + 7.5 + 0.3 = **19.3** | **не влезает** — отсюда «≥24 ГБ VRAM» и claim 23 GiB в карточке каталога |
| **fp8 онлайн (принято)** | ≈6 + 7.5 + 0.3 = **≈13.8** | замер: 12.4 простой, 15.3 пик на 1024² — запас ~0.6 GiB |
| int8 W8A8 | ≈13.8 | на `sm_120` не запускается (ошибка ядра) |
| bitsandbytes W4 / Comfy-Org int8-convrot, nvfp4 | ≈10.8 / 7.8–11.3 | не годится: ~17 GiB пика по документации / раскладка ComfyUI, vLLM её как diffusers-модель не грузит |

Диск: 32.9 GB весов + 9.85 GB раннера (перед деплоем 81 GB свободно, после — 63). Квант экономит **только
VRAM**: на диске лежит полный FP32-чекпойнт, `--quantization` работает на загрузке.

## Грабли (стоили времени 04.11)

1. **int8 на `sm_120` не работает.** `RuntimeError: dispatch_scaled_mm … Int8 not supported on SM120. Use FP8
   quantization instead`. Документация vLLM-Omni помечает «NVIDIA Blackwell (SM 100+) ✅», но 5070 Ti — это
   **sm_120**, отдельная ветка: int8-ядра cutlass туда не собраны.
2. **Без `ModelRoute` модель не видна в `/v1`.** GPUStack 2.2 публикует наружу маршруты, а не модели; лечится
   `POST /v2/model-routes` с `targets[].model_id`.
3. **Pull раннера и весов чуть не уронил ноду.** Свободное место ушло ниже порога эвикции kubelet (15 % ФС =
   35.4 GB), под выселен, image-GC containerd снёс все образы раннеров, кроме скачанного (rocm для `bge`,
   vLLM 0.25.1, VoxBox, beellama) — их пришлось качать при старте моделей. Правило: перед деплоем смотреть
   `df -h /` и держать **≥60 GB**, помня, что GC чистит образы остановленных моделей тоже.
4. **Правка параметров модели не перезапускает инстанс:** `PUT /v2/models/{id}` применяется только после
   `replicas 0` → `replicas 1`.

## Подготовка до сцены

- **Z1–Z2 — закрыто 04.11:** параметры карточки сверены с живым каталогом GPUStack 2.2.3 (`backend: vLLM`,
  `--omni`, `backend_version 0.22.1`); int8 не грузится, **fp8 грузится и работает**.
- **Z3 — закрыто 04.11:** веса (32.9 GB) и раннер скачаны, прогрев выполнен. **Перед показом** перепроверить
  `df -h /` и образ (`ctr -n k8s.io images ls | grep vllm0.22.1`) — иначе на сцене `ImagePullBackOff`.
- **Z4 — открыто:** промпты (по 5 английских и 5 русских, отобрать 3 сценических), зафиксировать
  `size`/`seed`; удачные картинки — в приватное хранилище, не в git.

## Фолбэк

1. fp8-путь не поднялся → тот же чекпойнт через `stable-diffusion.cpp` (`sd-server`) как custom backend
   (механика B0–B5 обкатана на BeeLlama): свой HTTP-API, Playground картинку не отрисует.
2. Диск не закрывается → кейс слайдом: «почему 6B-диффузия требует 24 ГБ и что с этим делает квант»,
   картинки из галереи модели, живого прогона нет.
3. Альтернатива `MOSS-Image-SFT` (id 21, проверена 22.11) на 16 ГБ **не поднялась**: fp8 — пик 15.18 из
   15.47 GiB, bf16 — 27 из 30 ГБ RAM; 50 шагов, CFG 3–4. Официальный путь для 16 ГБ закрыт, `Z-Image-Turbo`
   остаётся единственным.
