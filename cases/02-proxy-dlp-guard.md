# Кейс 02 — проксирование во внешнюю модель: DLP, страж, квоты

## Требования: модели на GPU

| Деплой в GPUStack | VRAM | Действие человека в UI |
|---|---|---|
| `Qwen3Guard-Gen-4B` — страж этого кейса, единственная модель на карте | ≈12.7 GiB (util 0.80) | `Start` |

- 780M свободна. Внешний маршрут — **`llm-svc.`**: статический ключ двумя входами, `x-api-key` для
  скриптов и `Authorization: Bearer` для OpenAI-клиентов. Второй вход `llm.` (JWT Keycloak) на паузе.
- Страж зовётся через стабильный `api.` с моделью `Qwen3Guard-Gen-4B`: ID один для обеих версий, поэтому
  в кейсе 03 исполняет `0.6B` под тем же ID и ничего не перенастраивается (`llm-proxy-spec` §P5).
- Сверка перед кейсом (иначе `403`/`503` на всех чатах): ключ `guard` имеет доступ к модели — прямой
  запрос отвечает `200`:
  ```bash
  curl -s -o /dev/null -w '%{http_code}\n' https://api.demo-ai-lab.ru/v1/chat/completions \
    -H "Authorization: Bearer *** из gpustack-admin.local.md>" -H 'Content-Type: application/json' \
    -d '{"model":"Qwen3Guard-Gen-4B","max_tokens":16,"messages":[{"role":"user","content":"погода"}]}'
  ```
  `403` = ключу не выдан доступ к модели (UI: API Keys → `guard` → Allowed models), `404` = в конфиге
  плагина неверное имя модели (нужно с заглавными).

## Сценарий показа

1. **Тезис:** «локальные модели — не религия: когда контур открыт наружу, защита должна быть на стенде,
   а не на честном слове».
2. **Обычный запрос** через `llm-svc` → `200`, ответ провайдера (проверено 01.11: 1.3 с, 99 токенов).
3. **DLP:** промпт с телефоном + вопрос «сколько цифр в этом номере?» → модель отвечает **0**: цифр она не
   видит, наружу ушёл `<PHONE>`, в ответе он восстановлен (`restore`).
4. **Страж:** джейлбрейк → `403` с вердиктом модели; сразу после — нормальный промпт → `200`, чтобы
   показать, что ложных блокировок нет.
5. **Квоты:** серия запросов выше `token_per_minute` → `429` на счётчике consumer'а.
6. **Предохранитель:** остановить стража в UI → следующий запрос получает `503 guard unavailable
   (fail-closed)`; включить обратно → `200`. Самый наглядный слайд: не «пропустили без проверки»,
   а «не проверили — не пропустили».

## Критерий успеха

Пять кодов в одном кейсе: `200` (обычный), «модель не видит цифр» (DLP), `403` (страж), `429` (квота),
`503` (fail-closed) — на одном маршруте, без правок в клиенте.

## Как показать работу DLP и стража

**DLP.** `llm-data-masking` переписывает тело запроса перед провайдером: `deny_openai: true`,
`failStrategy: FAIL_CLOSE`, `replace_roles` → `<PHONE>`, `<EMAIL>`, `<IP>`, `<KEY>`, у всех `restore: true`.
Ловушка: `restore` возвращает в ответ ровно то, что модель вернула как `<PHONE>`, поэтому ответ **внешне
идентичен немаскированному** — «попроси повторить» ничего не доказывает.

| Проба | Ответ модели | Вывод |
|---|---|---|
| «Сколько цифр в этом номере?» (+7 916 123-45-67) | `0` | цифр модель не видит → маскирование работает |
| «Замени каждую цифру на #» | текст вернулся без изменений (`+7 916 123-45-67`) | модель вернула `<PHONE>`, шлюз восстановил его |

Приём для сцены — спрашивать **производное** от ПДн (сколько цифр, сумма цифр, первая цифра словами):
`restore` это подделать не может, а немаскированный запрос модель отработает по существу.

Смотреть тут нечего: **в `ai_log` следов DLP нет** — плагин только переписывает тело, ни заголовков, ни
записи. Эталонное доказательство (разово, вне сцены): поднять в ns `llm` мини-мок OpenAI-эндпоинта,
направить на него регистр `deepseek` (`gitops/apps/llm/40-registries.yaml`), отправить PII-промпт и
прочитать тело в логе мока — там `<PHONE>`. После — вернуть регистр и перерендерить плагины
`scripts/llm_proxy_plugins.sh`.

**Страж.** `Qwen3Guard-Gen-4B` зовётся плагином `llm-qwen-guard` на каждый чат-запрос (`failOpen: false`,
timeout 8 с, адрес — `api.`, `llm-proxy-spec` §P5). Три кадра на сцене:
1. джейлбрейк → `403`, в теле `type: content_guard_blocked`, `reason: level=unsafe categories=…` — вердикт
   модели виден прямо в ответе, до провайдера запрос не дошёл;
2. сразу после — нормальный промпт → `200`: ложных блокировок нет;
3. `Stop` стража в UI → `503 guard unavailable (fail-closed)`, `Start` → `200` — главный слайд кейса.

Что модерация реально вызывалась — по инстансу стража:
`kubectl -n gpustack logs Qwen3Guard-Gen-4B-<hash> --tail=20` показывает `POST /v1/chat/completions` от
шлюза (в кейсе 03 исполнитель — `Qwen3Guard-Gen-0.6B-<hash>`).

## Как смотреть статистику проксирования и использование лимитов

Сводка по всем подам шлюза — `scripts/llm_stats.py` (таблица по запросам + итоги):

```bash
scripts/llm_stats.py                                   # последние 2000 строк
scripts/llm_stats.py --tail 20000 --since 30m --last 30
scripts/llm_stats.py --host llm-svc.demo-ai-lab.ru --json /tmp/stats.json
scripts/llm_stats.py --events-only                     # только 401/403/429/503 — что делали защиты
```

Колонки: `consumer` — кто звонил (`llm-svc`); `код` — ответ шлюза; `мс` — весь запрос, включая DLP и
стража; `in`/`out` — токены промпта и ответа по данным провайдера; `reason` — reasoning-токены из `out`
(у `deepseek-flash` их большинство, поэтому видимый текст короче); `кэш` — попадание в кэш промпта
провайдера; `провайдер_мс` — чистый провайдер (`llm_service_duration`); разница с `мс` и есть цена защиты.

Поля `ai_log` (JSON в access-логе, факт 01.11): `consumer`, `model`, `input_token`, `output_token`,
`total_token`, `input_token_details.cached_tokens`, `output_token_details.reasoning_tokens`,
`llm_service_duration`, `chat_round`, `response_type`, `chat_id`; рядом поля Envoy — `duration`,
`response_code_details`, `route_name`, `upstream_cluster`.

**Кто ответил** — по `response_code_details`:

| Действие | Как выглядит в логе | Что это значит |
|---|---|---|
| **Страж заблокировал** | `403` + `via_wasm::higress-system.llm-qwen-guard`, `ai_log` пустой | до провайдера не дошло; в теле `type: content_guard_blocked`, `reason: level=unsafe categories=…` |
| **Страж недоступен** | `503` + тот же плагин | fail-closed: «не проверили — не пропустили» |
| **Квота** | `429` + `via_wasm::higress-system.llm-token-ratelimit` | лимит токенов на `x-consumer` |
| **Нет идентичности** | `401` + `llm-key-auth::key-auth.no_key` | сервисный хост ждёт `x-api-key` |
| **Дошло до модели** | `200` + `via_upstream`, `ai_log` заполнен | страж и DLP пропустили |
| **DLP замаскировал** | **ничего**: ни `ai_log`, ни заголовков, ни записи | плагин только переписывает тело запроса |
| **DLP отказал** (только при `deny_words`) | `200` с `deny_code` + `via_wasm::…llm-data-masking` | денлист пуст (`deny_words: []`), не наблюдается |

Замер прогона 01.11: 38 запросов — `200×20`, `403×9` (страж), `401×6` (нет ключа), `503×2` (страж недоступен),
`0×1` (клиент оборвал); in 22 399 / out 3 605 токенов, средняя успешных 1 660 мс (p95 3 576), **цена защиты
≈183 мс**.

**Почему не `kubectl logs deploy/higress-gateway`:** у Deployment две реплики, и команда берёт одну
(«Found 2 pods, using pod/…») — цифры половинчатые. Скрипт читает `-l app=higress-gateway` со всех подов,
склеивает по времени и разбирает `ai_log` из каждой строки.

### Лимиты

`ai-token-ratelimit`: **60 000 ток/мин и 2 000 000 ток/сутки на `x-consumer`** — счётчик привязан к ключу, не
к человеку. Счётчики лежат в Valkey `valkey.dns:6379` под ключом
`higress-token-ratelimit:llm_route_quota:limit_by_per_consumer:<период>:x-mse-consumer:<consumer>`
(`86400` — суточное ведро, `60` — минутное).

- **Показать `429`:** серия запросов внутри минуты → `429` с `rejected_msg` плагина; сброс —
  `valkey-cli del` ключа consumer'а.
- **Как читать:** клиенты видят `429` и обычно понимают его как «кончились деньги провайдера», хотя до
  `ai-proxy`/DeepSeek запрос не доходит — это лимит стенда.
- **Факт 06.11:** реальное исчерпание суточной квоты (consumer `llm-svc-bearer`, 611 409 ток при лимите
  600 000) → `429`.
- **На зал:** при 15–20 гостях суточная квота выжигается быстро — поднять заранее или ограничить зал одним
  «демо-пулом».

Агрегаты — Prometheus стека консоли Higress (API под префиксом `/prometheus`, без него `404`); Grafana того
же стека открывается из консоли `hgc.`:

```bash
kubectl -n higress-system port-forward svc/higress-console-prometheus 9090:9090
curl -s 'http://127.0.0.1:9090/prometheus/api/v1/query?query=sum(rate(envoy_http_downstream_rq_total[5m]))'
```

## Что проверено и что осталось

| Элемент | Состояние |
|---|---|
| Прокси → провайдер, страж блокирует/пропускает, fail-closed | **проверено 01–02.11**: `200` / `403` / `503` |
| DLP-маскирование | **проверено поведенчески** («0 цифр»), в логах не видно |
| Лимиты `ai-token-ratelimit` | **проверено 06.11** на живом исчерпании суточной квоты (см. «Лимиты») |
| Трекинг пользователей | **не реализован**: `consumer` в `ai_log` различает только ключ (`llm-svc`), под одним ключом все запросы неразличимы; трейсинг-сервиса в архитектуре нет |

## Подготовка до сцены

- Заготовки промптов (обычный / с ПДн / джейлбрейк / серия для квоты) — чтобы не импровизировать на сцене.
- Демо-учётки — пул `demo01…`, но под статическим ключом `llm-svc` все падают в одно ведро consumer'а.

## Фолбэк

Провайдер недоступен → показать `401`/`503` как есть и разобрать их по логу; либо переключить на
локальную `gemma` и показать, что DLP работает и на локальном маршруте (квоты и страж настроены только
на внешнем).

## Хрупкость

С 2026-11-02 страж ходит через `api.` и от имени инстанса не зависит. Остались два места, где он падает:
1. **Ключ `guard` без доступа к `Qwen3Guard-Gen-4B`** → `403 Not allowed to access model` → fail-closed
   `503` на всех чатах; проверка — `curl` из «Требований».
2. **Имя модели в конфиге плагина** — `Qwen3Guard-Gen-4B` (с заглавными, как в API GPUStack): served-name
   `qwen3guard-gen-4b` через API даёт `404`.
