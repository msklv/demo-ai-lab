# Кейс 02 — Безопасное проксирование во внешнюю модель: DLP, страж, квоты, трекинг

## Требования: модели на GPU

| Деплой в GPUStack | Состояние | VRAM | Действие человека в UI |
|---|---|---|---|
| `Qwen3Guard-Gen-4B` | **включить** — единственная модель на карте | ≈12.7 GiB (util 0.80) | `Start` |
| `Qwen3.8-27B-UD`, `gemma-4-12B`, `whisper-turbo` | **выключить** | — | `Stop` |

- 780M: свободна.
- Обязательная сверка перед кейсом (иначе `503 guard unavailable`): Endpoints сервиса стража непустые —
  `kubectl -n gpustack get endpoints qwen3guard` → `192.168.10.252:<порт инстанса>`. Селектор и `targetPort` в
  `gitops/apps/llm/45-guard-endpoint.yaml` привязаны к имени инстанса и меняются при его пересоздании.
- Внешний маршрут: `llm-svc.` (статический ключ, для сервисов и скриптов зала) и `llm.` (JWT Keycloak, для клиентов с `client_credentials`).

## Сценарий показа (тезисно)

1. **Тезис:** «локальные модели — не религия; когда контур открыт наружу, защита должна быть на стенде, а не на честном слове».
2. **Обычный запрос** через `llm-svc` → `200`, ответ провайдера (это уже проверено 01.11: 1.3 с, 99 токенов).
3. **DLP:** промпт с телефоном/e-mail → пауза, затем на экране (лог Higress / трейс) видно, что наружу ушёл **плейсхолдер** `<PHONE>`, а в ответе он восстановлен (`restore`).
4. **Страж:** заведомо небезопасный промпт (джейлбрейк) → `403` с вердиктом модели; сразу после — нормальный промпт → `200`, чтобы показать, что ложных блокировок нет.
5. **Квоты:** серия запросов выше `token_per_minute` → `429` на конкретном `x-consumer` (а не «всё легло»).
6. **Предохранитель:** остановить стража в UI → следующий запрос получает `503 guard unavailable (fail-closed)`; включить обратно → `200`. Это самый наглядный слайд кейса: не «пропустили без проверки», а «не проверили — не пропустили».
7. **Трекинг пользователей** (если есть Langfuse `lng.`): два разных демо-пользователя → два разных трейса: кто, что спросил, сколько токенов, какие блокировки.

## Критерий успеха

Пять кодов в одном кейсе: `200` (обычный), «модель не видит цифр» (DLP), `403` (страж), `429` (квота), `503` (fail-closed при выключенном страже) — и всё это на одном маршруте, без правок в приложении-клиенте.

## Как смотреть статистику проксирования

**1. По каждому запросу — access-лог шлюза, поле `ai_log` (JSON).** Лучший вид для сцены: видно, кто, что, сколько токенов и сколько занял провайдер.

```bash
kubectl -n higress-system logs deploy/higress-gateway --tail=500 \
  | grep '"llm-svc.demo-ai-lab.ru"'
```

Поля `ai_log` (факт 2026-11-01): `consumer` (`llm-svc`, у JWT-пути — `azp`), `model`, `input_token`,
`output_token`, `total_token`, `input_token_details.cached_tokens`, `output_token_details.reasoning_tokens`,
`llm_service_duration` (мс, только провайдер), `chat_round`, `response_type`, `chat_id`.
Рядом — поля Envoy: `duration` (мс, весь запрос включая страж/DLP), `upstream_service_time`,
`response_code`, `route_name` (`llm/llm-svc`), `upstream_cluster` (`outbound|443||deepseek.dns`).

Сводка по всем подам шлюза — скрипт `scripts/llm_stats.py` (таблица по запросам + итоги):

```bash
scripts/llm_stats.py                                   # последние 2000 строк, оба хоста
scripts/llm_stats.py --tail 20000 --since 30m --last 30
scripts/llm_stats.py --host llm-svc.demo-ai-lab.ru --json /tmp/stats.json
```

**Почему не `kubectl logs deploy/higress-gateway`:** у Deployment две реплики, и `kubectl logs` берёт
одну («Found 2 pods, using pod/…») — цифры получаются половинчатые. Скрипт читает `-l app=higress-gateway`
со всех подов, склеивает по времени и разбирает `ai_log` из каждой строки.

Как читать таблицу:

| Колонка | Что значит |
|---|---|
| `consumer` | кто звонил: `llm-svc` (статический ключ) или `azp` JWT-клиента |
| `код` | HTTP-ответ шлюза (`200`, `403` страж, `429` квота, `503` fail-closed) |
| `мс` | весь запрос от входа до ответа — включая DLP и стража |
| `in` / `out` | токены промпта / ответа по данным провайдера |
| `reason` | из `out` — reasoning-токены (у `deepseek-flash` их большинство, поэтому видимый текст короче) |
| `кэш` | попадание в кэш промпта провайдера (повторный одинаковый префикс) |
| `провайдер_мс` | чистый провайдер (`llm_service_duration`); разница с `мс` — цена защиты |

Факт прогона 2026-11-01: 38 запросов, из них `200×20`, `403×9` (страж), `401×6` (нет ключа/токена),
`503×2` (страж был недоступен — fail-closed), `0×1` (клиент оборвал соединение); in 22 399 / out 3 605
токенов, средняя длительность успешных 1 660 мс (p95 3 576 мс), **цена защиты ≈ 183 мс**.

## Действия защит: что видно в логе, а что нет

Признак действия — поле `response_code_details`, и скрипт выводит его колонкой «кто ответил»:

| Действие | Как выглядит в логе | Что это значит |
|---|---|---|
| **Страж заблокировал** | `403` + `via_wasm::higress-system.llm-qwen-guard`, `ai_log` пустой | до провайдера не дошло; в теле ответа `type: content_guard_blocked` и `reason: level=unsafe categories=…` |
| **Страж недоступен** | `503` + тот же плагин | fail-closed: «не проверили — не пропустили» |
| **Квота** | `429` + `via_wasm::higress-system.llm-token-ratelimit` | лимит токенов на `x-consumer` |
| **Нет идентичности** | `401` + `llm-jwt-auth::jwt-auth.token_missing` или `llm-key-auth::key-auth.no_key` | не тот вход: JWT-хост ждёт токен, сервисный — `x-api-key` |
| **Дошло до модели** | `200` + `via_upstream`, `ai_log` заполнен | страж и DLP пропустили |
| **DLP замаскировал** | **ничего**: ни `ai_log`, ни заголовков, ни записи в логе | плагин только переписывает тело запроса — следа нет |
| **DLP отказал** (только при `deny_words`) | `200` с `deny_code` + `via_wasm::…llm-data-masking` | сработал денлист; сейчас `deny_words: []`, поэтому не наблюдается |

Живой срез «что делали защиты» — `scripts/llm_stats.py --events-only`: список только тех запросов,
на которые ответили плагины (401/403/429/503), без успешных вызовов.

Второе подтверждение по стражу — его собственный инстанс:
`kubectl -n gpustack logs qwen3guard-gen-4b-<hash> --tail=20` показывает `POST /v1/chat/completions`
от шлюза: значит модерация реально вызывалась, а не «включена на словах».

**2. Агрегаты — Prometheus стека консоли Higress.** Внимание: API отдаётся под префиксом `/prometheus`
(без него — `404`).

```bash
kubectl -n higress-system port-forward svc/higress-console-prometheus 9090:9090
curl -s 'http://127.0.0.1:9090/prometheus/api/v1/query?query=sum(envoy_http_downstream_rq_total)'
curl -s 'http://127.0.0.1:9090/prometheus/api/v1/query?query=sum(rate(envoy_http_downstream_rq_total[5m]))'
```

Факт 2026-11-01: 2044 метрики, `envoy_http_downstream_rq_total` = 10421, rate ≈ 1.34 rps. Grafana
(`higress-console-grafana:3000`) открывается из консоли `hgc.`.

**3. Квоты — Valkey (`valkey.dns:6379`).** Сейчас `dbsize = 0`, то есть счётчики `ai-token-ratelimit`
не наблюдаются (конфиг плагина корректный: `service_name: valkey.dns`, 60 000 ток/мин, 600 000 ток/сутки).
Вывод: шаг `429` надо **проверить замером**, а не считать работающим по конфигу.

## Как доказать маскирование

Ловушка: `replace_roles … restore: true` возвращает в ответ то, что модель вернула как `<PHONE>`, поэтому
ответ **внешне идентичен немаскированному** — «попроси повторить» ничего не доказывает.

Проверено 2026-11-01 на живом маршруте:

| Проба | Ответ модели | Вывод |
|---|---|---|
| «Сколько цифр в этом номере?» (+7 916 123-45-67) | `0` | цифр модель не видит → маскирование работает |
| «Замени каждую цифру на #» | текст вернулся без изменений (`+7 916 123-45-67`) | модель вернула `<PHONE>`, шлюз восстановил его (`restore`) |

Рабочий приём для сцены: спрашивать **производное** от ПДн (сколько цифр, сумма цифр, первая цифра
словами) — `restore` не может это подделать, а модель без маскирования ответит по существу.

Конфиг `llm-data-masking` (проверено): `deny_openai: true`, `failStrategy: FAIL_CLOSE`, `replace_roles` →
`<PHONE>`, `<EMAIL>`, `<IP>`, `<KEY>`, у всех `restore: true`. **В логе маскирование не видно** — в `ai_log`
нет полей о DLP, поэтому лог доказательством не является.

Эталонное доказательство (разово, вне сцены): поднять в ns `llm` мини-мок OpenAI-эндпоинта, который
логирует тело запроса, направить на него регистр `deepseek` (`gitops/apps/llm/40-registries.yaml`),
отправить PII-промпт, прочитать тело в логе мока — там будет `<PHONE>`. После — вернуть регистр и
перерендерить плагины `scripts/llm_proxy_plugins.sh`.

## Подготовка до сцены (блокеры)

- **Проверить то, что ещё не проверено:** маскирование (шаг 3), вердикт стража (шаг 4), квоты (шаг 5). Транспорт и fail-closed уже сняты 01.11.
- **Langfuse не установлен** — без него шаг 7 недоступен; сейчас трекинг показывается только логами шлюза. Для полноценного «трекинга пользователей» нужен проход спеки `langfuse-spec.md` (L1–L7).
- Демо-учётки: **пул** `demo01…`, не одна на всех — квоты и трейсы считаются по пользователю; одна общая учётка ломает и шаг 5, и шаг 7.
- Заготовки промптов (обычный / с ПДн / джейлбрейк / серия для квоты) — в сценарии показа, чтобы не импровизировать на сцене.
- Пропускная квота на зал: `ai-token-ratelimit` настроен на 60 000 ток/мин и 600 000 ток/сутки на `x-consumer` — при 15–20 гостях суточная квота выжигается быстро, поднять заранее или ограничить зал одним «демо-пулом».

## Фолбэк

Провайдер недоступен → показать `401`/`503` как есть и перейти к трекингу на логах шлюза; либо переключить на локальную `gemma` и показать, что защита всё равно та же (DLP работает и на локальном маршруте — но квоты/страж настроены только на внешнем).

## Хрупкость, о которой надо помнить

Порт и селектор сервиса стража (см. выше) — единственное место, где кейс ломается молча и выглядит как «сломался DeepSeek». Проверять за 5 минут до выхода, а не в момент показа.
