# Кейс 05 — RAG: эмбеддинги и реранк на стенде, генерация снаружи

## Требования: модели на GPU

| Деплой в GPUStack | Состояние | VRAM | Действие человека в UI |
|---|---|---|---|
| `Qwen3Guard-Gen-4B` (ID модели неизменен; `0.6B` — только в кейсе 03) | **включить** (без него внешний маршрут отдаёт 503) | ≈12.7 GiB на 5060 Ti | `Start` |
| `bge-m3` (эмбеддинги) | **включить** — **на 780M k8s-01** | 1.37 GiB GTT | `Start` |
| `bge-reranker-v2-m3` (реранк) | **включить** — **на 780M k8s-01** | ≈1.4 GiB GTT | `Start` |
| `Qwen3.8-27B-UD`, `gemma-4-12B`, `whisper-turbo` | **выключить** | — | `Stop` |

- 5060 Ti в этом кейсе занята только стражем: генерация **внешняя**, локальная LLM не нужна.
- 780M: два pooling-инстанса — **модели GPUStack** (бэкенд `vllm-rocm-igpu-custom`, образ
  `runner:rocm7.2-vllm0.25.1`, `HSA_OVERRIDE_GFX_VERSION=11.0.0`), селектор **`k8s-01:rocm:0`**
  (на ноде `UMA Frame Buffer Size` = 8G, fp16-веса и образ раннера лежат локально; клиенты не менялись).
  Проверять не «786M в свойствах», а **`rocm`-устройство в инстансе** и GTT на ноде
  (`mem_info_gtt_used` карты 780M): пара держит **2.77 из 11.63 GiB** (замер 04.11:
  2835 из 11908 MiB). Механика и грабли —
  `architecture/specs/gpustack-spec.md` §4.6 (проверено 2026-11-03).
- Внешняя генерация: `llm-svc.` (статический ключ) — то есть через DLP и страж, а не напрямую в провайдера.

## Сценарий показа (тезисно)

1. **Тезис:** «в RAG дорогая часть — не генерация, а поиск; поиск остался на стенде, наружу ушёл только отобранный контекст».
2. Гость открывает `rag.demo-ai-lab.ru` (SSO Keycloak), выбирает заранее проиндексированную базу.
3. Вопрос из зала → на экране топ-k чанков **после реранка** (`bge-reranker-v2-m3`), а не сырые результаты поиска.
4. Ответ генерации с цитатой на фрагмент документа.
5. **Контраст:** тот же вопрос задаём напрямую внешней модели (без RAG) — ответ общий, без опоры на документ стенда.
6. Показать, где считается эмбеддинг/реранк: инстансы на 780M, метрики/логи GPUStack; ни один чанк всего корпуса наружу не уходит — только выбранные.
7. (По желанию) тот же поиск через API — чтобы зал увидел, что это не «только UI».

## Критерий успеха

Ответ с ссылкой на конкретный фрагмент базы; в логах виден вызов `bge-m3` и `bge-reranker` на 780M до обращения к `llm-svc`; страж при этом включён (внешний вызов прошёл, а не 503).

## Подготовка до сцены (блокеры)

- **RAGFlow не развёрнут.** RAM-блокер на k8s-03 (стек ≈10–12 GiB) — вариант: ставить на k8s-01 (32 GiB) — там больше всего свободной RAM.
- ~~**`bge-m3` и `bge-reranker-v2-m3` не задеплоены**~~ — **снято 2026-11-03**: обе модели в GPUStack
  (`vllm-rocm-igpu-custom`), приёмка снята с публичного маршрута: `/v1/embeddings` → 200 (dim 1024, 0.18 с тёплый),
  `/v1/rerank` → 200 (0.08 с тёплый). Перед сценой — только `Start` в `Model Service → Deployments`.
  **Не запускать пару с дефолтными параметрами:** первый старт без `util 0.12` / `ctx 4096` валит
  ноду в GPU Hang (`gpustack-spec` §4.6, п. 4) — параметры должны быть в модели до `Start`.
- Индекс базы строится **до** сцены: первый парсинг документа 5+ минут.
- SSO для `rag.`: клиент Keycloak `rag` заведён по сиду, но интеграция RAGFlow↔Keycloak не проверялась.
- Учётная запись демо в RAGFlow (если SSO не заработает) — запасной вход.

## Фолбэк

**Основной фолбэк — RAG самого Open WebUI (`owu.demo-ai-lab.ru`)**: он с 2026-11-03 считает эмбеддинги
`bge-m3` и реранк `bge-reranker-v2-m3` на 780M (гибридный поиск, `owu-spec` §7.4). Сценарий тот же, что
задумывался для RAGFlow: загрузить документ в Knowledge → задать вопрос → показать топ-чанки после
реранка и ответ с опорой на фрагмент. Плюс: не требует отдельного стека RAGFlow (тот держит RAM-блокер),
и тот же вход по SSO.

Если и это недоступно — показать связку «эмбеддинг+реранк на 780M» прямым API (два запроса `curl`:
`/v1/embeddings`, `/v1/rerank`) и рассказать, что именно эти два вызова дают RAG; затем перейти к кейсу 06.
Кейс не должен держать остальную программу.
