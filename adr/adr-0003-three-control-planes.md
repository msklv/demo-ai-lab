# ADR-0003: Три control-plane (k8s-01/02/03), RAM-узлы и дисковые узлы разделены

- Дата: 2026-10-17
- Статус: **Accepted** (2026-10-17, владелец принял решение через опрос; п. 5 решён — вариант A, kube-vip VIP `192.168.10.240`)

## Контекст

1. 2026-10-17 в стенд добавлена нода `k8s-01` (192.168.10.250): R7 7840HS 8C/16T, **32Gi RAM**
   — самый мощный узел стенда по памяти; диск ZSPEED 512G с износом 11% и резервом TBW ≈100 TB
   (против ≈250+ TB у AirDisk на остальных нодах) — самый слабый по записям (замер 2026-10-17,
   `architecture/hardware-inventory.md`).
2. Владелец 2026-10-17 вывел решение: **мастерами будут три узла — k8s-01, k8s-02, k8s-03**.
   Ранее спецификация закладывала single control-plane на k8s-02 (`k8s-install-spec.md` §1,
   редакция 2026-10-16) — это решение заменяется.
3. В тот же день владелец **переустановил Ubuntu на k8s-02 и k8s-03** «для правильной системы
   хранения Longhorn»: живьём подтверждено — root-LV 100G, ~374G свободно в VG (было root-LV
   270G + ~204G в VG). Это возвращает стенд к исходному плану ADR-0002 (переустановка 02/03)
   и отменяет редакцию спеки «без переустановки» (2026-10-16). Побочные эффекты переустановки:
   узлы слезли со static-резерваций (RouterOS матчит lease по client-id, переустановка породила
   новый DUID; восстановлено в тот же день — client-id в static-записях обновлён через REST по
   явному разрешению владельца, .253/.254 bound) и потеряли containerd с CRI-конфигом,
   swap-подготовку, backend-netplan 10.20.20.0/26.

## Решение

1. **Топология: 3 control-plane — k8s-01, k8s-02, k8s-03** (stacked etcd, кворум 3, потеря
   одного мастера не останавливает кластер). k8s-04 — worker общего назначения с
   закреплённым LLM-инференсом (без taint'а, п. 2–3).
2. **Taint control-plane снять на всех трёх мастерах**; на k8s-04 taint `dedicated=llm`
   **не накладывается** (правка владельца 2026-10-17: на 04 можно и нужно запускать
   сервисы). Инференс защищается не изоляцией, а закреплением nodeSelector + приоритетом
   (priorityClass, preemption) и дисциплиной requests/limits у сервисов.
3. **Роли по узлам** (критерий: у кого что есть — RAM/CPU против TBW диска):
   - `k8s-01` — control-plane + **компьют-heavy сервисы** (RAGFlow разбор/индексация,
     OCR·Docling, qm/вынесенные рантаймы, BI): 32Gi RAM + 8C/16T; сознательно *компьют,
     а не данные* — диск самый слабый (LV нет, вне пула);
   - `k8s-02` — control-plane + **ingress (Higress, ADR-0001)** + GitOps (Argo CD): на .253
     уже смотрит NAT WAN 80/443;
   - `k8s-03` — control-plane + лёгкие сервисы (Open WebUI, каталоги);
   - `k8s-04` — **LLM-инференс (BeeLlama/GPUStack, nodeSelector) и сервисы**: здесь же
     data-heavy (PostgreSQL, ClickHouse, Qdrant, MinIO, Keycloak) — 28Gi RAM и диск в
     пуле Longhorn, БД локальны к своим репликам.
4. **Хранение: ADR-0002 в силе, Longhorn-пул = 3 узла (02/03/04) × LV 250G** ≈ 750G
   (~375G полезных при replica=2). **k8s-01 в пул НЕ включается**: диск ZSPEED с резервом
   ≈100 TB — не узел хранения; на нём запрещается дефолтный диск Longhorn
   (annotation `node.longhorn.io/create-default-disk: "false"`). Тяжёлые записи реплик
   идут на AirDisk с резервом ≈250+ TB. LV на 02/03/04 ещё не созданы — шаг F0 спеки.
5. **Точка входа API — ПРИНЯТ вариант A (2026-10-17): kube-vip, L2 VIP на LAN
   `192.168.10.240:6443`** — потеря k8s-02 переживает и API, и (позже, при переводе NAT
   на VIP) ingress. Обязательный спутник: зарезервировать `.240` в UI MikroTik (пул DHCP
   `.10–.254` иначе может выдать адрес Wi-Fi-клиенту) — действие владельца.
   Вариант B (статик `.253`) отклонён: k8s-02 оставался единой точкой API и ingress.
6. `controlPlaneEndpoint` попадает в certSANs apiserver — в SAN закладываются все три IP
   мастеров, оба имени варианта endpoint и `k8s-01/02/03`; список фиксируется в спеке до init.

## Последствия

- Расход RAM на мастерах 14Gi (02/03): etcd + apiserver + cm/scheduler + longhorn-manager +
  kubelet ≈ 2,5–3 Gi, остаётся ≈ 11 Gi на лёгкие сервисы; компьют-heavy — на 01, data-heavy — на 04.
- k8s-04 общий (LLM + БД на 28Gi): BeeLlama/GPUStack получают priorityClass выше сервисов
  и nodeSelector-закрепление; сервисы — строго с requests/limits. Риск oversubscription
  посреди демо — цена отказа от taint-изоляции.
- Переустановка 02/03 обнулила подготовку: `pb-k8s-prep.yaml` прогоняется заново на 01/02/03
  (на 04 подготовка в силе); backend p2p 10.20.20.0/26 (02↔03) для day-0 не нужен —
  Cilium ходит по LAN; восстановление netplan — отложенный пункт.
- p2p 2.5G связывает только мастера 02↔03; узел с основными данными (k8s-04) второй
  карты не имеет — трафик WAN→данные идёт через LAN (LAG 2×1G до роутера) — для демо-объёмов
  достаточно; при тяжёлых transfer'ах — вернуться к вопросу.
- Резервации .253/.254 восстановлены 2026-10-17 (bound) — prerequisite снят; на .253
  снова смотрит NAT, инфраструктура имён/IP (ansible inventory, `/etc/hosts`, доки) сходится.
  При любой будущей переустановке узла — обновлять client-id в его static-записи DHCP.
- Спецификация установки (`k8s-install-spec.md`) правится под 3 CP (F1: init на k8s-01,
  join `--control-plane` на 02/03, worker 04).

## Альтернативы (рассмотрены и отклонены)

- **Оставить single CP на 02, k8s-01 = data-worker** — отклонено решением владельца:
  три мастера дают отказоустойчивость API/etcd; RAM 01 при этом всё равно используется
  под данные.
- **k8s-01 в пул Longhorn (LV 250G)** — отклонено: самый изношенный диск стенда (11%,
  резерв ≈100 TB), правило `hardware-inventory.md` — тяжёлые записи не на него.
- **Выделенные мастера (control-plane taint'ы сохранены)** — отклонено: 14Gi мастеров
  под лёгкие сервисы — осознанный компромисс (иначе нагружать негде).
- **Сохранить на k8s-04 taint `dedicated=llm:NoSchedule` (только LLM)** — отклонено
  правкой владельца 2026-10-17: самый мощный воркер должен нести и сервисы; taint лечил
  перерасход RAM, который теперь закрывается requests/limits + priorityClass.
- **external etcd (3 отдельных ноды)** — отклонено: нод больше нет, stacked etcd для
  3-узловой панели стандарта demo-стенда достаточно.
